# Учёт времени, напоминания и права

## Работа сотрудника

В меню есть раздел **Тайм-менеджмент**. Любой сотрудник, включая руководителя, может:

- запустить таймер на доступной активной задаче и остановить его после работы;
- внести интервал вручную (до 24 часов за одну запись, без будущих дат);
- отметить сложность от 1 до 5, причину и комментарий;
- удалить собственную ошибочную запись; действие сохраняется в истории задачи.

Интервалы одного человека не пересекаются, даже если они относятся к разным задачам или workspace. Одновременно разрешён один таймер. Таймер хранится в БД и переживает перезагрузку страницы. Завершение/архивация задачи останавливает её таймеры.

Причины: без затруднений, неясное ТЗ, ожидание ответа/согласования, техническая проблема, переделка, отвлечения, другая. Для сложности 4–5 требуется причина, для «другой» — комментарий. Причина характеризует всю запись времени: разные виды работы лучше фиксировать отдельными интервалами.

Отчёт показывает записанное время за 7/30 дней или всё время, задачи с наибольшим временем, среднюю заявленную сложность, причины и журнал. Превышение оценки отмечается при превышении одновременно 20% и 30 минут. При фильтрации периода время обрезается границами периода; оценка задачи остаётся полной. Отсутствие оценки не означает нулевую оценку. Затраченное время не является рейтингом продуктивности, а указанная причина не доказывает причинно-следственную связь.

Даты ручного ввода используют часовой пояс браузера. В БД хранятся абсолютные моменты времени; AI-дедлайны интерпретируются в часовом поясе профиля.

## Напоминания

Стандартные пороги: за **24, 5 и 1 час** до срока; отдельно — просрочка и предстоящее начало задачи. Назначение задачи создаёт уведомление сразу. Статусы `todo`, `queued`, `in_progress`, `under_review`, `blocked` участвуют в проверке срока; завершённые и архивные задачи исключены.

Уведомления получает назначенный активный исполнитель, состоящий в workspace, независимо от должности. В настройках можно отключить напоминания и задать до шести целых порогов 1–168 часов. Переключатель overduePush управляет просрочкой; название историческое, реальный канал сейчас — приложение.

За один проход отправляется наиболее актуальный порог. Например, после простоя до дедлайна осталось 40 минут: придёт уведомление текущего часового порога, а не пачка за 24/5/1 час. Повторные проходы и удаление уведомления из списка не создают дублей. Новый исполнитель или изменённый срок образуют новый набор напоминаний.

`npm run dev` и `npm run start` запускают Next.js и отдельный обработчик напоминаний. Обработчик проверяет БД каждую минуту; при ошибке пишет сообщение и повторяет на следующем проходе. Завершение одного дочернего процесса останавливает второй. Для внешнего супервизора обработчик можно запустить отдельно:

```bash
npm run notifications:worker
npm run notifications:worker -- --once
```

Чтение списка уведомлений дополнительно проверяет задачи текущего пользователя; это резервный механизм, а не замена фонового процесса. Заголовок приложения опрашивает уведомления раз в минуту.

На serverless-платформе постоянный процесс не работает: разверните worker отдельно как долгоживущий сервис с тем же DATABASE_URL. Нельзя считать закрытые вкладки обслуживаемыми, если worker остановлен. Автоматическая доставка email, Web Push, SMS и Telegram не подключена.

## Оргструктура

Workspace — граница организации. В **Команде** отображается доступная часть дерева и статистика назначенных задач. Имя должности произвольное; технические роли определяют полномочия, а не престиж должности.

- owner/admin: весь workspace;
- member/viewer со scope `self`: назначенные ему и созданные им задачи;
- scope `team`: свои задачи и задачи сотрудников ниже по цепочке руководства;
- scope `workspace`: делегированная видимость всего workspace;
- viewer не может изменять задачи или записывать время.

Глобальный admin остаётся явно привилегированной платформенной ролью. Руководители демо-отделов имеют member + team, а не admin всего workspace. Настройка руководителя и области доступа доступна owner/admin; циклы и руководители из другого workspace запрещены. Прямое назначение второй роли owner запрещено: есть отдельный атомарный endpoint передачи владения.

Списки, детали, аналитика, календарь, справочники и AI-контекст используют серверный scope. Данные в интерфейсе не являются механизмом защиты. Показатель «нарушения» не рассчитывается: его бизнес-определение отсутствует.

## Дополнительные возможности

- Удаление задачи заменено архивацией; восстановление — из списка «Архив» и карточки задачи. История сохраняется.
- В карточке задачи доступны блокирующие зависимости и история действий. Циклы зависимостей запрещены, завершение при незавершённых блокирующих задачах отклоняется.
- Вложения до 5 МБ доступны по правам задачи, учитываются в квоте workspace и скачиваются как файлы, а не исполняемый контент. Локальные файлы находятся в `.data/uploads` или FILE_STORAGE_PATH. Для нескольких production-инстансов нужен общий постоянный том или отдельный storage-адаптер; локальный serverless-диск непригоден. Бэкап БД не заменяет резервное копирование файлов.
- Приглашения создаются администратором, действуют 3 дня и привязаны к email. В БД хранится только хеш кода. Передача кода — вручную по доверенному каналу. Принятие требует входа с тем же email и не повышает уже существующую роль.
- Сессии подписаны и зарегистрированы в БД. Выход отзывает текущую; смена пароля аннулирует прежние; в настройках безопасности можно отзывать устройства и выходить везде. Production требует AUTH_SECRET длиной минимум 32 символа.

## API

| Метод | Маршрут | Назначение |
|---|---|---|
| POST | /api/time-entries | Таймер или ручной интервал |
| PATCH | /api/time-entries/:id | Остановить свой таймер с причиной |
| DELETE | /api/time-entries/:id | Удалить свою запись с аудитом |
| GET | /api/time-management?workspaceId=…&from=…&to=…&userId=… | Отчёт в пределах scope |
| GET/PATCH | /api/organization | Дерево / подчинённость и scope |
| GET | /api/tasks/:id/activity | История и видимые зависимости |
| POST/DELETE | /api/tasks/:id/dependencies | Добавить / убрать зависимость |
| GET/POST | /api/tasks/:id/attachments | Файлы задачи |
| GET/DELETE | /api/attachments/:id | Скачать / удалить файл |
| GET/POST/DELETE | /api/invitations | Приглашения workspace |
| POST | /api/invitations/accept | Принять код |
| POST | /api/workspaces/:id/ownership | Передача владения |
| GET/DELETE | /api/auth/sessions | Список / отзыв одной или всех сессий |

## Проверка

```bash
npm test
npm run typecheck
npm run lint
npm run build
npm run test:production
```

Тесты используют временные SQLite-базы, включая обновление старой схемы. Исходная `.data/taskflow.db` не очищается. Для ручного тестирования реального AI нужны свои провайдер и ключ; локальные расчёты времени и напоминания от LLM не зависят.


Production smoke-проверка создаёт временную базу, запускает собранное приложение с worker на свободном порту и проверяет scope, запись времени, Origin, отзыв сессий, смену пароля и сценарий нового владельца workspace. Нужна предварительная `npm run build`; рабочая база не используется.

AI-планировщик учитывает часовой пояс профиля, личные события календаря и незавершённые блокирующие зависимости. Отдельные кадровые графики смен, отпуска и утверждение табелей не реализованы: отсутствие календарного события не доказывает доступность человека. Контекст генератора содержит оценочный объём открытых задач; похожие заголовки в видимой области исключаются из новых предложений. Это не гарантирует семантическую уникальность или качество реальной LLM.
