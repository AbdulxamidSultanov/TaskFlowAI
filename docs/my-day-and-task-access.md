# «Мой день», контроль команды и участие в задачах

## Экраны

- `/dashboard` — **Мой день**: «Сегодня», «Просрочено», «Требует моего действия». Старый dashboard сохранён как `/overview` («Обзор»).
- `/team-control` — **Контроль команды**: просрочки, блокировки, ожидание проверки; фильтры по исполнителю, статусу и диапазону срока в часовом поясе профиля.
- Карточка задачи `/tasks?task=<id>` — сдача и проверка результата, блокировка/помощник, запрос действия, участники и их отделы.
- В «Команде» доработано существующее дерево: поиск, сворачивание веток, круги с инициалами, линии, список доступных задач выбранного человека.

«Сегодня» определяется по сроку или началу в текущий локальный день профиля пользователя, с учётом границ дня/DST. Закрытые и архивные задачи исключены. Персональные задачи — назначенные пользователю или явно выданные ему; запросы действия показываются только их адресату с подходящим разрешением. Группы могут пересекаться, общий счётчик — размер объединения уникальных ID из показанных групп, а не сумма счётчиков. Пустые группы отображаются явно.

## Матрица прав

| Основание | Просмотр | Работа с результатом | Комментарии / файлы / время | Исполнитель / сроки / участники / архив |
|---|---|---|---|---|
| owner/admin workspace, существующий global admin | В пределах существующих административных полномочий | Управление; проверка чужого результата | Да | Да |
| Супервейзор с `team` | Задачи назначенных подчинённых, включая вложенные команды | Управление и проверка чужого результата | Да | Да для своих командных задач |
| Исполнитель, не viewer | Назначенные ему задачи | Рабочий статус, сдача; собственную проверку принять нельзя | Да | Нет, если нет отдельного управленческого основания |
| Явный contributor | Только выданная задача | Запрос/ответ, блокировка; помощь со снятием блока, если указан помощником | Да | Нет |
| Явный viewer / workspace viewer | Только разрешённая область просмотра | Нет | Нет | Нет |

Scope `workspace` у обычного member делегирует видимость, а не административные действия. Создатель задачи сам по себе не получает бессрочный доступ к задачам вне своей области. Супервейзор может управлять созданной им собственной задачей; принятие собственного результата запрещено.

Структура подчинения и роль человека в дереве не заменяют проверки задачи. Основные функции: `taskScope` для выборок и `taskPermissions`/`requireTaskPermission` для отдельных действий. DTO задач содержит разрешения только как подсказку интерфейсу; сервер вычисляет их заново при каждом действии.

Одинаковая видимость применяется к спискам/поиску, деталям, счётчикам, аналитике, комментариям, файлам, уведомлениям и AI. Выдача одной задачи не открывает API проекта или отдела. Участники и базовая информация о проекте/отделе в контексте карточки не являются доступом к остальным сущностям.

## Межотдельные участники

Управляющий задачей выбирает активного участника того же workspace, в том числе другого отдела, и выдаёт `viewer` или `contributor`. Пользователя из другой организации сначала надо легально пригласить в workspace; выдача task grant сама этого не делает.

Сотрудник или contributor не может добавить себя, изменить состав участников или расширить свою роль. Удаление grant проверяется немедленно на backend. Другое основание (исполнитель, законная область команды, admin) сохраняется. При полном отзыве/понижении участия закрываются запросы к этому человеку, сбрасываются его назначения помощником/проверяющим и останавливается его таймер на задаче. История и уже созданные рабочие записи сохраняются.

Содержимое, уже загруженное в браузер, нельзя «забрать из памяти» пользователя. Новые запросы запрещаются сразу, карточка обновляется при фокусе и периодически; при отказе загрузки отображается недоступность, а не старые данные задачи.

## Проверка результата

У задачи есть `requiresReview` и проверяющий. При создании с проверкой по умолчанию выбирается уполномоченный руководитель исполнителя. Проверяющий из другого отдела сначала должен получить contributor-доступ; поле reviewer само по себе доступ не выдаёт.

1. Исполнитель нажимает «Передать на проверку».
2. Сохраняются `submittedAt` и `under_review`; `completedAt` остаётся пустым, создаётся запрос проверки.
3. Проверяющий/уполномоченный супервейзор принимает: `completed`, `reviewedAt`, `reviewedById`, `completedAt`.
4. Возврат требует комментарий минимум 3 символа; комментарий попадает в обсуждение, задача — в `in_progress`.

Если проверка не нужна, сдача сразу завершает задачу. Generic PATCH не позволяет обойти этот процесс. Отмена — явный статус `cancelled`; завершённые и отменённые не считаются просроченными и не получают напоминаний о сроке.

## Блокировки и запросы

Новая блокировка требует причину минимум 3 символа. Сохраняются причина, дата, автор и помощник. Указанный помощник должен уже иметь право работать с задачей. Без явного помощника проверяется руководитель исполнителя; если у него нет доступа, автоматический доступ не создаётся и уведомление ему не отправляется.

«Снять блокировку» разрешено управляющему либо автору блока/указанному помощнику при наличии права участия. Причина и решение остаются в истории. Исторические blocked-задачи без причины отображаются как «Причина пока не указана», а не заполняются вымышленным объяснением.

Запрос ответа — отдельная сущность `task_action_requests` с адресатом и конкретной причиной. «Ответить» требует текст; ответ сохраняется как комментарий, запрос закрывается. Запрос проверки/снятия блока закрывается соответствующим workflow-действием.

## Автоматизации

Переиспользуется отдельный worker `scripts/notification-worker.ts`, запускаемый вместе с `npm run dev`/`npm run start`, либо отдельно `npm run notifications:worker`.

- Приближение срока: существующие индивидуальные пороги сохраняются; при отсутствии настроек — `TASK_REMINDER_HOURS` или 24 часа. Изменённый срок образует новый план, незамеченные старые напоминания удаляются. Закрытие/архив отменяет ненужные напоминания.
- Блокировка: worker отправляет помощнику или уполномоченному руководителю уведомление с задачей, причиной и действием. Доступ проверяется перед отправкой, выдачи доступа нет.
- `reminder_deliveries` обеспечивает дедупликацию при повторных запусках, включая удаление уведомления из inbox. Невидимые задачи исключены и из unread/counts, и из прямого обращения к уведомлению.

Внешние каналы не подключались: уведомления внутри приложения. Worker должен оставаться запущенным независимо от браузера; для serverless нужен отдельный постоянный процесс, как описано в `docs/time-management.md`.

## Миграция и API

Миграция `0006_tired_madame_masque.sql` сохраняет прежние задачи и связанные записи, добавляет статус отмены, поля review/block, `task_participants` и `task_action_requests`, восстанавливает существующие SQL-триггеры после перестройки таблицы. Для старых `under_review` подготовлены запросы проверки. Для старых блокировок сохраняются известные дата/автор, но причина не придумывается.

Применение: `npm run db:migrate`. Локальная резервная копия создаётся и проверяется автоматически. **Не выполнять db:seed/db:reset для обновления рабочей базы.**

Новые API:

- `GET /api/my-day?workspaceId=…`
- `GET /api/team-control?workspaceId=…&assigneeId=…&status=…&fromDay=YYYY-MM-DD&toDay=YYYY-MM-DD`
- `POST /api/tasks/:id/workflow`: `submit`, `accept`, `rework`, `block`, `unblock`, `request`, `resolve`, `cancel`
- `GET/POST/DELETE /api/tasks/:id/participants`
- `GET /api/tasks/:id/candidates` — только для управляющего участниками задачи.

## Проверки

`npm test`, `npm run typecheck`, `npm run lint`, `npm run build`, `npm run test:production`. Тесты используют временные БД. Дополнительно проверяются desktop/mobile через Chromium. Реальный LLM, email и push не нужны для этих сценариев и не выдаются за проверенные интеграции.

Проверено в облачной среде: 29 тестов прошли; typecheck, lint и production build успешны. Production smoke проверяет запуск web+worker, выдачу/отзыв доступа к одной задаче, вложения, запреты изменений и сокрытие уведомлений после отзыва. В Chromium пройдены сдача результата, доработка, приёмка, снятие блока, поиск в дереве, английская локализация, desktop и ширина 390 px. Для browser/HTTP-тестов использованы отдельные базы. После миграции рабочей SQLite: integrity_check=ok, foreign_key_check пуст, количество строк прежних таблиц совпадает с резервной копией.
