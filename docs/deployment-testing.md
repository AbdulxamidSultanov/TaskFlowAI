# Развёртывание для тестирования

## Рекомендация: всё на своём компьютере

Для фиксированных 26 тестовых аккаунтов лучше один процесс Next.js с API, SQLite и отдельным worker на том же компьютере. Это сохраняет загрузку файлов и минутные уведомления без платных внешних сервисов. Компьютер должен оставаться включённым. Отдельный backend не требуется: он уже находится в `src/app/api`.

Нужны Git и Node.js 24 LTS; на Windows удобно использовать WSL2 Ubuntu.

```bash
git clone https://github.com/AbdulxamidSultanov/TaskFlowAI.git
cd TaskFlowAI
git checkout feat/time-management-reminders
npm ci
```

Создайте `.env.local` по `.env.example`. Для production задайте `AUTH_SECRET` минимум 32 символа; получить случайное значение:

```bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

База по умолчанию `.data/taskflow.db`, файлы `.data/uploads`. Для совершенно новой пустой базы один раз:

```bash
npm run db:migrate
npm run db:seed
```

Если уже перенесли существующую базу, выполняйте только `npm run db:migrate`. Не запускайте seed/reset поверх рабочих данных. Для переноса остановите приложение, скопируйте всю `.data` с файлами, затем запускайте миграции. База и пароли не входят в Git/PR.

```bash
npm run build
npm run start -- --hostname 127.0.0.1
```

Откройте http://localhost:3000/ru/login. Данные входа: [test-accounts.md](test-accounts.md). `start` запускает web и worker вместе. Остановка: Ctrl+C. Для разработки можно `npm run dev`.

Для телефона в своей сети используйте `npm run dev -- --hostname 0.0.0.0`, откройте `http://<локальный-IP-компьютера>:3000/ru/login`; разрешите порт 3000 только в частной сети. Это режим разработки для теста, не публичный хостинг. Production с защищёнными cookie для удалённых устройств требует HTTPS reverse proxy, например Caddy, и `APP_ORIGINS=https://<ваш-домен>`. Для постоянного доступа лучше небольшой VPS: те же команды, постоянный диск, HTTPS и supervisor/systemd для `npm run start`.

Резервная копия: `npm run db:backup`; каталог файлов копируйте отдельно. Не коммитьте `.env.local`, токены и SQLite.

## Если нужен именно Vercel + Turso

Vercel размещает Next.js и API вместе. Локальная SQLite и постоянные файлы внутри Vercel не подходят: файловая система функций эфемерна. Подключите удалённую libSQL-базу Turso.

1. Создайте базу и токен в Turso. Локально укажите `DATABASE_URL=libsql://...`, `DATABASE_AUTH_TOKEN=...` в `.env.local`.
2. Сделайте snapshot существующей удалённой базы. Задайте `CONFIRM_REMOTE_MIGRATION=1` и выполните `npm run db:migrate`. Для новой пустой тестовой базы затем один раз `npm run db:seed`. Для существующей — только миграция. Эти команды создают свежий набор тестовых аккаунтов и задач; существующая локальная база сама не переносится.
3. Импортируйте репозиторий/нужную ветку в Vercel, preset Next.js, build `npm run build`, установка `npm ci`, Node.js 24.x. Не добавляйте миграции и seed в build.
4. В Environment Variables добавьте URL/токен Turso, случайный `AUTH_SECRET` и `APP_ORIGINS=https://<проект>.vercel.app`. Не задавайте `NEXT_PUBLIC_API_URL`: браузер должен использовать API того же origin. AI можно оставить без ключа — демонстрационный режим явно обозначен.
5. Выполните Deploy. Проверьте `/api/health`, вход работника, его задачи и запрет чужой задачи.

### Настроенный production на Vercel

Проект `notformes-projects/taskflowai` использует Node.js 24, Next.js, Turso и функции
в регионе `dub1`, рядом с базой в Ирландии. Домен: https://taskflowai-app.vercel.app.
`DATABASE_URL`, `DATABASE_AUTH_TOKEN`, `AUTH_SECRET` и `CRON_SECRET` задаются на Vercel;
значения секретов не входят в Git. Существующая защита Deployment Protection сохраняется.
Не копируйте production-базу и ключи в preview; для тестирования отдельной ветки нужна отдельная база.

Вложения хранятся в **приватном Vercel Blob**, подключённом к production-проекту.
`BLOB_READ_WRITE_TOKEN` (или OIDC с `BLOB_STORE_ID`) включает этот режим. Браузер
загружает до 5 МиБ напрямую в Blob: сервер выдаёт подписанное разрешение с привязкой
к пользователю, задаче, имени, размеру и сроку, затем проверяет объект перед регистрацией.
Это обходит лимит тела запроса Vercel Functions. Скачивание идёт через API с проверкой
прав задачи и потоковым ответом. Ссылки на публичные объекты не создаются.
Квота workspace и история изменения сохраняются в одной транзакции; повторное
подтверждение одного разрешения не увеличивает квоту повторно.
Если браузер закрылся до подтверждения, загруженный объект может остаться без записи:
при обслуживании хранилища удаляйте только проверенные старые бесхозные объекты.

Напоминания запускает **Vercel Schedules** из `vercel.json` каждые 10 минут, даже
когда приложение закрыто. `/api/cron/reminders` требует `Authorization: Bearer <CRON_SECRET>`.
Повторная доставка безопасна благодаря существующим ключам дедупликации.
На Hobby платформа может добавлять до 15 минут задержки (jitter); это не
гарантия доставки точно по минуте. Расписание использует максимум 4464 плановых
запусков за 31 день, без перехода на платный тариф. Локальные `dev`/`start` по-прежнему
могут использовать отдельный минутный worker; на Vercel он не нужен.
Уведомления остаются внутри приложения: email/push-провайдеры не подключены.

Локальный запуск без Blob сохраняет файлы в `.data/uploads`. При запуске на Vercel
без настроенного постоянного хранилища запись отклоняется, чтобы файлы не терялись.
Существующие локальные вложения автоматически в Blob не переносятся: их необходимо
перенести отдельно с сохранением связей (в подключённой базе перед настройкой
таблицы вложений не было). AI без `AI_API_KEY` остаётся в явно обозначенном деморежиме.

После изменения переменных выполните новый production-деплой; миграции и seed
не входят в команду сборки. Проверяйте health, вход, права сотрудника, загрузку и
скачивание файлов и последние запуски `task-reminders`.

## Фиксированный набор пользователей

Все 26 аккаунтов уже существуют в текущей базе и имеют проверенные пароли. Новые не нужны. Форма регистрации остаётся частью существующего приложения: требование не создавать новые аккаунты не отключает регистрацию технически. Для закрытого теста не публикуйте сервис с демонстрационными паролями в открытый интернет; используйте закрытую сеть/доступ по приглашению. Для публичного стенда предварительно ограничьте доступ на уровне хостинга либо отключите регистрацию и смените демонстрационные пароли.
